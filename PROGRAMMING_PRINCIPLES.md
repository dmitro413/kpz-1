
## 1. Separation of Concerns (SoC) — Розділення обов'язків
Проєкт побудовано на архітектурному патерні **MVC**. Це дозволяє розділити логіку обробки запитів, представлення даних та самі дані.

**Контролери** (наприклад, [`Controllers/ShopController.cs`](CourseWork/Controllers/ShopController.cs)) обробляють запити.

**Моделі** (наприклад, [`Models/Product.cs`](CourseWork/Models/Product.cs)) описують структуру даних.

**Представлення** (наприклад, [`Views/Shop/IndexSHOP.cshtml`](CourseWork/Views/Shop/IndexSHOP.cshtml)) відповідають лише за HTML-інтерфейс.

## 2. Don't Repeat Yourself (DRY) — Не повторюй себе
Принцип спрямований на уникнення дублювання інформації та логіки.
*   **Як реалізовано:** Спільна логіка для різних типів даних винесена в узагальнені структури або методи розширення. Це дозволяє змінювати логіку в одному місці.
*   **Приклад:** Використання методів розширення для сесії у файлі [`Extensions/SessionExtensions.cs`](CourseWork/Extensions/SessionExtensions.cs). Замість того, щоб у кожному контролері писати складний код серіалізації JSON, використовується один універсальний метод `SetObject`.

  ## 3. Single Responsibility Principle (SRP) — Принцип єдиної відповідальності
Кожен об'єкт або метод повинен мати лише одну відповідальність.
*   **Як реалізовано:** Класи розділені за їх функціональним призначенням. Технічні завдання (робота з сесією, валідація, керування базою) виконуються різними класами.
*   **Приклад:** Файл [`Models/LoginViewModel.cs`](CourseWork/Models/LoginViewModel.cs) відповідає виключно за структуру даних для входу користувача та її валідацію. Він не знає нічого про базу даних або логіку авторизації.

  ## 4. Dependency Inversion Principle (DIP) — Принцип інверсії залежностей
Високорівневі модулі не повинні залежати від низькорівневих модулів. Обидва повинні залежати від абстракцій. (У даному проєкті реалізовано через передачу залежностей у конструктор).
*   **Як реалізовано:** Контролери не створюють об'єкти для роботи з базою даних самостійно. Вони отримують готові інструменти через конструктор.
*   **Приклад:** У файлі [`Controllers/AccountController.cs`](CourseWork/Controllers/AccountController.cs) контролер отримує об'єкт `UnitOfWork` ззовні, що дозволяє легко замінити його в майбутньому без зміни коду самого контролера.

  ## 5. Encapsulation — Інкапсуляція
Принцип, що полягає в приховуванні внутрішньої реалізації об'єкта від зовнішнього світу та наданні доступу лише через публічні методи.
*   **Як реалізовано:** Дані про кількість товарів на складі та складні алгоритми їх списання приховані. Зовнішній код просто викликає команду.
*   **Приклад:** Метод `DecreaseStockAsync` у файлі [`Repositories/ProductBatchRepository.cs`](CourseWork/Data/Repositories/ProductBatchRepository.cs). Контролер не знає, з якої саме партії списується товар, він лише викликає метод, який керує цим процесом.

  ## 6. KISS (Keep It Simple, Stupid) — Роби це простіше
Принцип проектування, який стверджує, що більшість систем працюють краще, якщо вони залишаються простими.
*   **Як реалізовано:** Логіка контролерів залишається лінійною та зрозумілою. Відсутні переускладнені конструкції або надлишкова абстракція там, де це не потрібно.
*   **Приклад:** Метод `Login` у файлі [`Controllers/AccountController.cs`](CourseWork/Controllers/AccountController.cs). Процес перевірки користувача та створення сесії розбитий на прості, послідовні кроки, які легко читати та відлагоджувати.
